# Input
**Description:** Text/number/date/select form fields. The shipped CSS defines **two distinct treatments** for what is conceptually the same field role — see `COMPONENTS.md` § Known inconsistencies #3 — so this spec documents both tiers rather than picking one.

## Anatomy
Single-line native form control (`<input>`, `<select>`), bordered rectangle, no icon/prefix/suffix decoration, no floating label — every field is paired with an external `<strong>`/placeholder for its label instead of an internal one.

## Variants

| Variant | Classes / selector | Key values | When to use |
| --- | --- | --- | --- |
| Filter/weekbar field | `.weekbar input`, `.weekbar select`, `.filters input`, `.filters select` | border 1px `colors.border`, `rounded.select` (9px), bg `colors.surface`, `padding:9px 10px` | `input#weekDate` (date), `select#savedWeeks`, `input#q` (search, has `placeholder="Tìm mã hoặc tên chỉ tiêu..."`), `select#groupFilter`, `select#changeFilter`, `select#sortBy` |
| Table progress input | `.progressInput` | border 1px `colors.border-input` (`#cad4e1`), `rounded.input` (8px), `padding:7px`, `width:90px`, `text-align:right` | Per-row "Tuần này" % field: `type="number" min="0" max="100" step="0.1"`, suffixed with a literal `%` sibling text node |
| Table note input | `.noteInput` | border 1px `colors.border-input`, `rounded.input`, `padding:7px`, `width:100%;min-width:170px` | Per-row "Ghi chú tuần" free-text field, `placeholder="Nội dung đã làm / vướng mắc..."` |

## States
<!-- Exactly these five rows, in this order — treatments as rendered by the shipped CSS. -->

| State | Treatment |
| --- | --- |
| default | per-variant border/radius/padding above; all fields inherit `font:inherit` (`dashboard.html:17`) |
| hover | **Not styled** — no `:hover` rule for any input/select selector |
| focus | **Not styled** — no `:focus` rule authored; browser UA default focus ring/outline only |
| active | **Not styled** — no `:active` rule (the shared `.btn:active` press effect does not apply to form fields) |
| disabled | **Unreachable** — no `disabled`/`readonly` attribute is ever set on any input/select in the markup, and no `:disabled` CSS rule exists |

## Tokens Used
- `colors.surface`, `colors.border`, `colors.border-input`, `colors.text`
- `rounded.select` (9px), `rounded.input` (8px)
- `spacing.sm` (9px 10px, filter tier), `spacing.2xs` (7px, table tier)
- `typography.body` (inherited)

## Do / Don't

- ✅ Use the filter/weekbar tier for anything living inside `.weekbar` or `.filters` — don't mix in the table-cell border/radius values there.
- ✅ Use the table-cell tier only inside `#tbody` rows (`.progressInput`/`.noteInput`) — matches the shipped app exactly.
- ✅ Clamp `.progressInput` values to `[0,100]` on change (`setProgress()`, `dashboard.html:832-834`) — silently, no inline error message (matches shipped behavior, see `Screens/` States section).
- ❌ Don't add a visible validation/error state — none exists; out-of-range input is silently clamped, not rejected with feedback.

## Normalize on redesign
1. Unify the two border/radius treatments into one shared Input style (see `COMPONENTS.md` § Known inconsistencies #3).
2. Add an inline validation message when `.progressInput` clamps an out-of-range value, instead of silently correcting it with no feedback.
